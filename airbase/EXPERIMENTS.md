## §2026-07-22　纯视觉伺服 斜下接触（相机 -50° + cy 视线角闭环）

### 设置
- 场景：缩小飞机（~20m，顶面≈6m）+ 相机下倾 **-50°**（对齐从高空滑向地面的滑降角，目标全程居中）。
- 方法：**纯指纹视觉伺服**（不用世界模型）。`--face-ned` 初始一次性对准 → 之后纯视觉；
  `cx→yaw`（横向对准）、`cy→下降率`（**视线角闭环**，让目标保持画面中心、沿视线接触）。
- 起点 50m，`--v-down 2.0`（滑降角 ~34°）。落盘 `signals.csv`/`run.h5`/`viz_dump/`。

### 离线信号（`check_target_signal.py`，`airbase_tgt1_100m`）
- cost/peak/mass vs 真实距离**单调**：Spearman **+0.81 / −0.85 / −0.93**。
- 结论：信号沿接近轨迹**有梯度**。**但这是必要非充分**——只测了"沿好路靠近时单调"，
  **没测**判别性（干扰物）、部位可分、闭环控制。实跑踩的坑都在这后半张考卷。

### 指纹判别性（rviz 热力图 + 多模板）
- 整机/机头模板热力图**整机全红**（`plan_viz_node` 用绝对刻度 sim≥0.6 才红，非 min-max 假象）
  → 指纹只分"**飞机 vs 背景**"，**不分部位**。
- 根因：`proto = 模板所有 patch 求平均` → 塌成"通用飞机表面特征"；远距离整机才占几个 patch。
- 远处车辆、跑道标线**易被误标红**：DINO 语义特征相似，**非 UE 渲染问题**，换工具同样存在。

### 闭环两条对照（50m 起，-50°，v_down 2.0）
| 模板 | 结果 | 末位置/高度 | 问题 |
|---|---|---|---|
| **机头** | 位置最好，居中填满画面 | (-60.4,-14.4)，**14.4m** | `mass=0.20` 提前停（整机模板 mass 早饱和），**未接触** |
| **红星** | 判别性看似干净（mass 全程低） | (-74.8,-22.6)，4.4m | 因 mass 低→不减速→**水平冲过头 ~11m 脱靶**，末端降到目标后方空地、误匹配跑道标线 |

- 终点帧证据：机头末帧飞机居中填满；红星末帧几乎全是空地、飞机只剩边缘。
- **横向对准全程可靠**（`cx≈0`）；cy 视线角闭环**修好了旧"落在目标前面"的根因**（旧版开环匀速降→目标沉出画面）。

### 待修点（下一步）
1. **停太高（机头）** → 用 `--stop-alt`（本次新增，按高度判接触，弃早饱和+噪声的 mass 判停）。
   机头 + `--stop-alt 7` 大概率可直接接触。
2. **水平冲过头（红星）** → 减速不能只靠 mass；拟加**"低空自动减速前进"**（不依赖 mass，低空即减速），
   任何模板都不会冲过头。
3. 部位可分性（机头 vs 尾翼）**目前不成立**（整机全红）；如需分部位，走"更聚焦小模板 + 峰值/top-k 代替质心平均"或"近距离才分部位"的两段式，另开验证。

### 产物
- `outputs/runs/servo/{整机,机头,红星,驾驶舱,机头2}_0722_*/`：`signals.csv` + `run.h5` + `viz_dump/`
- 各 run 下 `replay.mp4`（带标注：绿十字=画面中心、红圈=指纹质心 cx/cy）

### 运维坑：PX4/UE 联调的重启规律（血泪，务必遵守）
反复重启把三方联调搞挂调了很久，最后测清楚了每次重跑的**最省事配方**：

> **UE 里 End PIE → 重新 Play（几秒，不用关编辑器）** + **起一个全新 PX4** + **跑一次伺服**。

对照实测：

| 操作 | 结果 |
|---|---|
| 同一个正在跑的关卡直接跑第二次（不重置） | ❌ 连不上（4560 不重建） |
| **停关卡 + 重新 Play**，UE 编辑器不关 | ✅ 可以（最省事） |
| 关掉整个 UE 重开 | ✅ 可以但没必要，慢 |

- **根因**：① PX4 SITL 的模拟器链路（TCP 4560）**一次性**——伺服脚本退出会 `client.disconnect()`
  断开 ProjectAirSim，PX4 的 4560 随之断且不再接受新连接，故 PX4 每次必须重起；
  ② ProjectAirSim 在 UE 里的 px4-api 桥，客户端断开后**不自动复位**，需 End PIE + 重新 Play 才干净。
- **失败症状**：伺服卡在"连接 PX4"、`ss` 看 TCP 4560 为空、`udpin 14540` 收不到心跳。
  只要看到这三样，别瞎查——直接按上面配方重来一次。
- 切忌 UE 关卡还开着时反复杀/重启 PX4，会把 UE 的桥搞进坏状态，越弄越乱。

### 大坑：MAVSDK 连不上 PX4 的真正根因 = 14580/14540 端口撞车（时好时坏的元凶）
症状：伺服卡在 `连接 PX4: udpin://0.0.0.0:14540`，但 **TCP 4560 是 ESTAB、PX4 完全正常**
（在 `pxh>` 敲 `commander takeoff` 无人机能起飞，证明 PX4↔仿真走 4560 好好的）。问题纯在 14540 这条 MAVSDK 链路。

- **根因**：PX4 的 offboard 链路是 **instance #1**（`mavlink status` 里 `mode: Onboard, UDP 14580→14540`）。
  而 config `robot_quadrotor_px4_airbase.jsonc` 的 `control-port-local/remote: 14580` 让 **ProjectAirSim 也去连 14580**。
  两个抢同一条链路，谁先连谁当 partner：
  - MAVSDK 先抢到 → partner=WSL 本地 → PX4 把 14540 数据发给 MAVSDK → **成功**（早期几次的运气）
  - ProjectAirSim(Windows 172.21.192.1) 先抢到 → PX4 把 14540 数据**全发去 Windows** → WSL 的 MAVSDK 一个包收不到 → **卡死**
- **铁证**：`mavlink status` 的 instance #1 显示 `partner IP: 172.21.192.1`、`Received Messages: sysid:135`
  （sysid 135 = ProjectAirSim，非 QGC——实测没开地面站也这样）。裸 python 监听 14540 八秒零包。
- 这是**抢占竞态**，不是死锁，所以"时好时坏"。脚本里先载场景(ProjectAirSim 连 14580)再连 MAVSDK，本该总是 ProjectAirSim 赢。
- 三条链路各司其职（别混）：`4560`=ProjectAirSim⇄PX4 传感器/电机(仿真必需)；`14580`=ProjectAirSim 多余的控制链(方案B用不到但它照连)；`14540`=PX4→MAVSDK offboard(被上面挤掉)。

**解法（不改文件、不重编译）：给 MAVSDK 单开一条 ProjectAirSim 碰不到的链路（14549）：**
1. UE Play → 起 PX4 → 跑伺服（`--mav-url udpout://127.0.0.1:14549`）→ 伺服停在"连接 PX4"干等（不会崩）。
2. 等 PX4 打印 `Simulator connected`、`pxh>` 活了，在 pxh 敲：`mavlink start -u 14549 -r 4000000`。
3. PX4 立刻在 14549 开链路，MAVSDK(udpout 主动连，像 QGC)接上 → arm → 爬升。
- 只用 **14549 一个端口**，两处对齐（pxh `-u 14549` ↔ 伺服 `udpout://127.0.0.1:14549`），ProjectAirSim 只认 14580、碰不到 14549。
- 想省掉每次手敲 `mavlink start`，可把那行写进 PX4 启动脚本 `px4-rc.mavlink`（会改 PX4 文件，暂不做）。

## §2026-07-27　端口撞车根治（不碰 PX4 文件）+ 启动手册

### 根因从 PX4 源码坐实（07-24 只是抓包推断，这次读到了出处）
`~/PX4-Autopilot/ROMFS/px4fmu_common/init.d-posix/px4-rc.mavlink` 的 offboard 链路：

```sh
udp_offboard_port_local=$((14580+px4_instance))    # 14580
udp_offboard_port_remote=$((14540+px4_instance))   # 14540
mavlink start -x -u $udp_offboard_port_local -r 4000000 -f -m onboard -o $udp_offboard_port_remote
```

- **不带 `-t`**（且我们没设 `PX4_NET_INTERFACE`，故也没有 `-n/-p`）→ PX4 默认把 14540 发到 **`127.0.0.1`**，
  即 WSL 本机、MAVSDK 正在监听的地方 → **本该一直好使**。
- 但只要有人往 14580 发包，PX4 就把 partner 切成那个来源 IP。ProjectAirSim(Windows) 的
  `control-port-remote: 14580` 正是在干这事 → 14540 整条流被拽去 Windows → MAVSDK 饿死。
- 这解释了 07-24 观察到的一切：`mavlink status` instance #1 的 `partner IP: 172.21.192.1`、
  裸 python 监听 14540 八秒零包、TCP 4560 却完全正常。**抢占竞态，故"时好时坏"。**

### 修法：改我们仓库的 config，让 ProjectAirSim 的控制链打空
`sim_config/robot_quadrotor_px4_airbase.jsonc`：`control-port-remote/local` **14580 → 14588**
（PX4 全套端口 14580/14540、18570/14550、14280/14030、13030/13280 里没有 14588，它从不监听）。

- ProjectAirSim 的控制链发进空气——**方案B 本来就不用它**（控制走 MAVSDK，仿真走 TCP 4560）。
- PX4 的 offboard 链路保持 localhost 模式 → MAVSDK 用脚本默认 `udpin://0.0.0.0:14540` 直接连上。
- **收益：彻底不用再手敲 `mavlink start -u 14549`**，也不用 `--mav-url` 传参。
- **为什么不写进 PX4 的 `px4-rc.mavlink`**：那是 PX4 仓库的文件，换设备/重装就丢，
  且会掩盖真正的端口冲突。原则定为 **PX4 保持原版，所有配置留在本仓库**（随 git 走）。
- ⚠️ **待实测**：ProjectAirSim 的 px4-api 桥在收不到控制链回包时会不会拒绝初始化（理论上不会，
  4560 才是仿真必需链路）。若真出问题，回退就是把这两行改回 14580 + 用 14549 兜底方案。

## §2026-07-28　闭环甩头根治 + 分段距离标定 + **架构定案（三条件消融）**

### 一、PX4 闭环甩头 300° —— 根因是"转向没停稳就交接"

**症状**：进入视觉伺服闭环的第一拍，航向从 -163° 甩到 +135°，之后偏到东向一路飞走，
目标立刻出画面。0724、0728 的每一次运行都复现。

**排查过程（用 `src/airsim/px4_yaw_probe.py` 隔离测试，摘掉 DINO 和相机只留飞控层）**：

| 段 | 条件 | 最大航向偏差 |
|---|---|---|
| A | 位置设定值 5Hz（对照组） | 3.0° ✅ |
| B | 速度设定值 5Hz | 1.6° ✅ |
| C | 速度设定值 2.9Hz（=闭环实际频率） | 0.4° ✅ |
| D | +航向用实测值（相对指令，同伺服） | 0.1° ✅ |
| E | +边飞边降 down=1.1 | 0.1° ✅ |
| F | +每拍阻塞 0.2s（模拟 DINO 卡事件循环） | 0.1° ✅ |
| **G** | **大角度转向"刚跨过 3° 阈值"就切速度设定值** | **80.7° ❌** |

**根因**：对准判据只看"偏差 <3°"，此时飞机**仍带角速度**（实测交接瞬间 +103°/s）。
一切到速度设定值，PX4 就在目标航向两侧持续振荡，8 秒收不住。
A~F 每段之前都已停稳，所以从没复现过 —— 这是 G 段才暴露出来的条件。

**修法**（`servo_closed_loop_px4.py`）：对准判据改成「偏差 <3° **且连续保持 `--yaw-settle` 秒**」
（默认 2.0s），中途超出即计时清零；超时 30→40s。

**同时改的（方向对但不修这个 bug，为真机保留）**：闭环下发从
`set_velocity_body(VelocityBodyYawspeed)` 改成 `set_velocity_ned(VelocityNedYaw)`，
航向给**绝对值**且以**实测航向**为基准往前推一拍（不对指令自积分，真机跟不上时不会跑飞）。

**排除的假设**（都有数据，别重复走）：旋翼混控错配（与厂商参考配置逐字相同）、
下发频率过低、DINO 阻塞事件循环、下降耦合、EKF 航向漂移。

### 二、控制参数：`--v-down 1.6` 不是默认值

从两次运行的 signals.csv 最小二乘反推增益，发现老那次成功运行用的是 **`--v-down 1.6`**，
而脚本默认是 1.2（`k_vert=1.5`、`v_forward=3.0` 两者一致）。默认值下滑坡度浅 33%，
飞到指纹能工作的距离时还挂在 30m，会从目标头顶飞过去。**跑接触必须显式传 `--v-down 1.6`**。

### 三、停止判据是互斥的（易踩）

```python
if args.stop_alt is not None and -dz <= args.stop_alt:   # 给了 stop-alt → 只看高度
if args.stop_alt is None and mass >= args.mass_stop:     # 没给 stop-alt → 才看"贴近"
```
**一给 `--stop-alt`，接触判据就被关掉了。** 要真接触就别传 `--stop-alt`。

### 四、`mass` 的语义与分段距离标定

`mass = sigmoid((sim - 0.35) * 20).mean()` —— 是**响应面积占比**，不是相似度。
`mass=0.2` ≈ 256 个 patch 里约 50 个响应 ≈ 目标占画面 1/5。
阈值 0.35 + sharpness 20 近似阶跃，所以 mass 对 peak 极度非线性、**逐帧跳变是正常的**
（每次成功都是 0.0x → 0.2 一步跳过去）。要看连续量用 `peak`。

**指纹强度 vs 距离（全部历史运行分箱，peak 中位数）**：

| 距离 | 整机模板 | 机头模板 |
|---|---|---|
| 0-10m | 0.452 | 0.418 |
| 10-20m | 0.377 | 0.252 |
| 20-30m | **0.208** | 0.156 |
| 30-40m | **0.205** | 0.100 |
| 40-50m | **0.197** | 0.123 |
| 50-70m | **0.216** | 0.140 |

**结论：两种模板在 20m 以外都是平的**（整机 0.197~0.216 全程无梯度；机头还非单调）。
→ **指纹不能当远段规划的 cost**，有效工作半径 ≈ 20m。

**相机几何硬限制**（FrontCamera 俯仰 -50°、FOV 90°、16:9 → 垂直 FOV 58.7°）：

| 画面位置 | 对应水平距离 |
|---|---|
| 上边缘 | 2.66 × 高度 |
| 中心 | 0.84 × 高度 |
| **下边缘** | **0.19 × 高度** |

目标近到 0.19×高度就滑出画面下沿，**最后约 5m 是反应式控制的盲区**。

**部位贴近点（成功运行的终点，mass≥0.15）**：

| 模板 | 成功次数 | 贴近点 (n,e) | 高度 |
|---|---|---|---|
| 机头 | 4 | (-51.9, -12.0) | 20.4m |
| 尾翼 | 1 | (-52.9, -20.3) | 24.8m |
| 红星 | 3 | (-71.8, -22.1) | 8.2m |
| 整机 | 5 | (-52.4, -15.2) | 21.5m |

**同一架飞机、同一个坐标，不同部位的贴近点相距 6~20m** —— 部位信息藏在飞机朝向里，
坐标给不了。这是"坐标做不到的事"的第一条硬证据。

### 五、架构定案：三条件消融（取代之前的"两段式管线"）

之前设想的「远段世界模型 + 近段伺服」**作废** —— 那样世界模型无处安放：
远段空旷机场里已知坐标直线飞就是最优解，近段又被伺服占了。

**正确摆法：伺服是对照组，不是管线的一段。**

```
出生 ──直线飞已知坐标(脚手架, 论文诚实写成"粗定位已知")──▶ 25m 球
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
   A 纯伺服(基线)            B 纯世界模型+MPPI          C 世界模型定方位 + 伺服精跟踪
   25m ──▶ 失效点              25m ──▶ 接触                 25m ──▶ 接触
```

| 条件 | 25m→接触谁在飞 | 回答什么 |
|---|---|---|
| A | 反应式指纹伺服 | 基线：不用世界模型能多好 |
| B | WM+MPPI 直接出速度指令 | 世界模型能否独立完成近场 |
| C | WM+MPPI 定切入方位/下滑线 → 伺服精跟踪 | 结合是否最好 |

最终架构 = B 和 C 里赢的那个；A 永远只是对照。
**A↔C 的消融最干净**：同一个伺服控制器，唯一差别是前面有没有世界模型引导。

**预判 C 赢**，因为短板互补：MPPI 空间分辨率 0.9m/步（dt=0.3 × 3m/s）做不了像素级对准；
反应式伺服无前瞻，结构上做不了"从哪一侧切进去"的决策
（0728 机头失败正是方位漂到 -32° 后再也纠不回来）。

**世界模型在这 20m 里比伺服多做的三件事**（都不需要改场景、不需要加障碍物）：
1. **部位 = 视觉概念 + 目标朝向的函数**，切入方位是远距离就要做的前瞻决策
2. **视野保持 / 盲区**（<0.19×高度），反应式已证明失效
3. **目标自遮挡**（机身挡住机头/驾驶舱），随视角变化

**分段距离（新）**：

| 段 | 距离 | 谁飞 | 性质 |
|---|---|---|---|
| 粗定位 | 67 → 25m | 坐标直线 | 脚手架，三条件共用，不算贡献 |
| **近场** | **25m → 接触** | **A / B / C** | **对比实验区** |

25m 的依据：部位指纹 17~20m 起有信号，留 5m 余量给纠偏。
三条件共用：同一起点球、同一部位模板、同一 PX4 下发链路、同一成功判据（mass≥0.2）。

## §2026-07-29　远段 cost 换读出方式 —— **否定结果**（三条 episode × 五模板 × 五读出）

> **结论先写：远段(>20m)没有任何一种现成读出能给 MPPI 用，换读出方式解决不了。**
> 本次结果未支持通过更换读出方式扩展远段工作范围。

### 动机与来源

看到 DreamNav（arXiv 2607.04352）的 dual-cue 设计（SuperGlue 稀疏匹配 → 稠密位移场
与原图 concat），想到"显式几何对应也许比语义相似度随距离衰减得慢"，据此检验
§2026-07-28 记录的"指纹在 20m 外全平"到底是 **DINO 特征本身不判别**，还是只是
**读出方式**（patch·proto 取峰值/面积）不行。

**没有采用该论文的 SuperGlue**：先用同一份 DINO 特征换读出，这样赢了能归因到"读出方式"，
而不是"换了个更强的模型"。（事后看这个选择是对的 —— 见下面的机制分析。）

### 实验

`src/airsim/check_correspondence_signal.py`（新）。同一 episode、同一模板、同一份
DINO 特征、同一标准化统计量，只换读出：

| 读出 | 定义 |
|---|---|
| `peak` / `mass` | 现有指纹（基线）。patch 特征 · 模板 proto 的峰值 / 过阈面积 |
| `dino_nn` | 帧 patch 与模板 patch **互为最近邻**且 sim≥0.5 的匹配对数 |
| `dino_conc` | 上述匹配点的空间聚集度 = 1/(1+到质心平均距离) |
| `sift_n` | SIFT + 比值检验的良匹配数（纯几何、无语义） |

数据：`airbase_tgt1_50m` / `_100m` / `_tgt1` 三条 × `{整机,机头,尾翼,红星,驾驶舱}`
五模板 = 15 组，182~265 帧/条。本地 CPU 可跑（帧特征与模板无关，一次编码多模板复用）。

### 结果 1：单调性（Spearman ρ，≥20m 远段）

> ⚠️ **本节数字已于 07-29 当天修正两次方法学错误**（由 Codex 评审指出，已复核属实）：
> 1. **Spearman 未处理并列秩**：原用 `argsort(argsort(a))`，对并列值按出现顺序强行分配
>    不同秩，**系统性高估**相关性。`dino_nn` 并列率 **88%**、`sift_n` **94%**（整数计数），
>    受影响最大。已改为**并列取平均秩**（`_rank()`）。
> 2. **标准化统计量取自被测 episode 自身 = 测试信息泄漏**，使信号偏乐观。已改为从
>    **独立的** `--stats-episode` 取（默认 `airbase_tgt1_50m`；测 50m 那条时用 100m 的）。
>
> 修正前后对比（15 组）：
>
> | 读出 | 符号正确 | \|ρ\|>0.5 可用 | 中位 ρ |
> |---|---|---|---|
> | peak | 12 → **13**/15 | 8 → **10**/15 | -0.534 → **-0.582** |
> | mass | 12 → **13**/15 | 11 → **12**/15 | -0.638 → **-0.715** |
> | dino_nn | 15 → **14**/15 | **14 → 8**/15 | -0.706 → -0.739 |
> | sift_n | 13 → 13/15 | 9 → **8**/15 | -0.682 → -0.618 |
>
> **`dino_nn` 的可用率从 14/15 塌到 8/15，比 `mass` 还差 → 下文"dino_nn 看似大胜"的说法
> 全部撤回。** 修正后 ρ 的排序与 SNR 的排序终于一致（mass > peak > dino_nn），
> 结论反而更自洽。**否定结论（远段全军覆没）不受影响，且更可信。**

**以下是修正后的数**（≥20m 远段，15 组 = 3 episode × 5 模板）：

| 读出 | 符号正确 | \|ρ\|>0.5 可用 | 中位 ρ | 最差 ρ |
|---|---|---|---|---|
| peak | 13/15 | 10/15 | -0.582 | **+0.522** |
| **mass** | **13/15** | **12/15** | **-0.715** | **+0.735** |
| dino_nn | 14/15 | 8/15 | -0.739 | +0.455 |
| sift_n | 13/15 | 8/15 | -0.618 | +0.270 |
| dino_conc | — | — | 多组退化为常数(ρ=nan) | — |

### 结果 2：SNR —— **推翻结果 1 的结论**

ρ 只看排序，**不看幅度与噪声之比**。补算 SNR = |该尺度上的 cost 变化| / 段内噪声（20m 带内线性拟合残差 std）：

| 读出 | 20-40m 单步(0.9m) | 20-40m 全时域(13.5m) | 40-70m 全时域 |
|---|---|---|---|
| mass | 0.14 | **2.16** | 1.29 |
| peak | 0.12 | **1.82** | 1.02 |
| **dino_nn** | 0.09 | **1.29** | 0.76 |
| dino_conc | 0.12 | 1.87 | 0.49 |
| sift_n | 0.07 | 1.05 | 0.45 |

**单步尺度上全部只有 0.03~0.14** —— 信号比噪声低一到两个数量级。
MPPI 一步只走 0.9m（dt=0.3 × 3m/s），候选动作之间根本分辨不开。
按 15 步时域折算后也全部落在 1~2，**正是过去被判定"用不动"的量级**。

**按 SNR 排序，`dino_nn` 反而比 `mass`/`peak` 差。**（SNR 不涉及秩，
不受上面两处方法学错误影响；修正 ρ 之后两个指标的排序变一致了。）

### 机制分析（为什么 ρ 好但 SNR 差）

`dino_nn` 数的是"有多少 patch 匹配上模板"，**本质仍是面积度量**，只是不带硬阈值、走排序。
不带阈值 → 排序更稳（ρ 好）；也更容易被噪声推动 → 幅噪比更差（SNR 差）。
**跟"几何对应"这个叙事无关**，DreamNav 的 dual-cue 对本任务没有可借鉴之处
（另：该论文成功判据是 10m、成功率仅 23.51%、航向 MAE 38.78°，本身也不是强证据）。

### 站得住的三条

1. **远段(>20m)全军覆没**：五种读出的 SNR 都在"已证明不够"的量级，换读出解决不了。
2. **`peak`/`mass` 会给反方向梯度**（红星模板 ρ=+0.52/+0.24）。独立于 SNR，且很危险 ——
   MPPI 拿它当远段 cost 会**主动往远飞**。这条解释了过去闭环里一些莫名其妙的行为。
3. **`sift_n` 排除**，两项指标都不占优 → **LightGlue/SuperGlue 不用装**，省一个依赖。
   `dino_conc` 亦不可用（符号仅 11/15 正确），但代码保留在脚本里当诊断列。

### 对架构的影响：**没有推翻，反而补强**

指向的正是 §2026-07-28 已定的方案 —— **远段(>25m)用坐标直线飞，不指望视觉 cost**；
近场(<25m)本来就有信号（20-40m 段 mass SNR 2.16，且越近越好）。
三条件消融的实验区定在 25m 以内，恰好落在**有信号的一侧**。

### 方法论教训（写下来防止再犯）

- **ρ 单调 ≠ MPPI 能用。** 验收 cost 必须同时看 SNR，且要按 MPPI 的**单步空间尺度**算，
  不能只看整条轨迹的秩相关。
- **秩相关必须处理并列。** 整数/离散指标（计数类）并列率可达 90%+，
  `argsort(argsort())` 会把 ρ 虚报一大截。本仓库两个脚本都犯过，已修。
- **标准化统计量绝不能取自被测数据。** 用被测 episode 自身估 z_mean/z_std 是测试信息泄漏。
  更根本的修法（待做）：训练阶段一次性生成固定的 `feature_stats`，所有目标/测试共用。
- 单条轨迹的 ρ 里混着"信号 vs 视角/高度/光照"，距离与这些量是绑死的。
- 拿到一篇论文先问"它的指标有多强"（这篇 SR 23.5%）和"它的机制在我这里是否同构"，
  再决定要不要花时间验证。
- **自己的结论要主动找人复核。** 本节两处错误都是外部评审（Codex）发现的，
  且都指向"让结论看起来更好"的方向 —— 这类错误自查最不容易发现。

### 四、分割相机：**可用，但默认配置下是废的**

**默认 ID 全部撞车。** `get_segmentation_id_map()` 实测：
`staticmeshactor_0/1/14/16/18/20/22/24` → **全是 83**（地面、四架飞机、汽车、天空球同色）。

**用该公式复现实测的 17 条映射，17/17 全部命中**（`drone1`→29、`sm_compass`→219、`cameraactor_0`→135…）。

**修法（不改代码）**：运行时调 `set_segmentation_id_by_name(name, id, is_name_regex=False, use_owner_name=True)`。
覆盖时走的是**字符串精确比较**（`UnrealHelpers.h:234`），不经过哈希 → 数字参与比较 → 只命中一个 actor。

### 五、深度相机：**是米制的** —— 推翻 07-17 的结论

把三个目标的包围盒中心投影到像素，在该处采样深度原值与真实几何距离对比：

| 目标 | 真实距离 | 深度原值 | 比值 |
|---|---|---|---|
| 一号 @80m | 100.8 m | 101 | **1.002** |
| 二号 @80m | 197.9 m | 197 | 0.996 |
| 一号 @140m | 152.1 m | 152 | **0.999** |
| 三号 @140m | 346.9 m | 344 | 0.992 |
| 汽车 @80m | 101.8 m | 96 | 0.943 |

全为整数、相邻取值间隔中位数 **1.0** → **原值就是米，量化步长 1m**。
0.99x 与汽车的 0.943 不是误差：投影点是**包围盒中心**（物体内部），深度测的是**可见表面**，
理应偏近（汽车盒高 8.73m，中心比顶面低 4.4m，偏差 5.8m 正好对上）。

**`65504` 是天空/无命中哨兵**（float16 最大有限值）。80m 时画面无天空（max=299）；
140m 时顶边漏进 **1 个**天空像素 → 65504 出现，且它与掩膜第 5 个颜色（1px）**重合率 100%**。

**根因不在传感器，在消费端**：`depth_map.py:47` 写的是 `raw / 1000.0`，注释还标着"单位=毫米"
（按 ROS 的 16UC1=毫米 惯例）。真实 100m 被当成 0.1m → 点全塌相机跟前。
旧记忆里"扣掉天空后原始值均值 ~176 → 0.18m，尺度明显错"反而是本次结论的佐证：
**176 就是 176 米**，水平朝前的相机看远景完全合理。

**已修**：`airbase/src/airsim/depth_map.py` 去掉 `/1000.0`，docstring 钉上本次实测证据
（防止以后有人按 ROS 惯例改回去）。`SKY_RAW = 65000` 的哨兵处理本来就是对的，未动。

**连带**：`--map-max-range` 默认 40m 在旧 bug 下形同虚设（深度恒 <40）。单位修对后它变成真限制，
而画面中心地面点斜距 ≈ 高度/sin50°（30m高→39m，50m高→65m）。**默认值未改**（建图从未启用：
2754 个 viz_dump npz 中 0 个含点云），只在 help 里写明该按作业高度调大。

## §2026-07-31　采集脚本近场改造（通向 B/C 的第一步）

### 为什么是它

`airbase/weights/` 只有 DINO 权重、`outputs/datasets/` 是空的 → **B/C 是"尚未实现"而非"跑了没效果"**。
需要先准备机场采集数据，并使采集方式覆盖近场任务。

### 改了什么（`collect_episode.py` 重写）

| 项 | 采集方式 | 用途 |
| --- | --- | --- |
| 起点 | **以目标为心的球内随机站位** | 覆盖目标各方位的接近过程 |
| 动作 | **`move_by_velocity_body_frame_async`** | 保持采集与控制的动作坐标系一致 |
| 步数 | **100 步 / 10s** | 8~25m 十秒就走完 |
| 批量 | **一次起飞串 N 条**（`--num`） | 减少重载与起降等待 |
| 存储 | **RGB + 深度(uint16 米) + 分割(调色板 BGR)** | 深度进控制/latent；分割只进 evaluator |
| 目标真值 | **OOB 存进 h5 attrs** | evaluator L1 的地基，闭环零开销、可离线补算 |

轨迹模板换成机体系的五类：`approach / orbit / correct / drift / scan`
—— 只采接近的话，模型没见过"偏了怎么办"。

### 站位采样：修正了 07-30 待办里写的参数

07-30 写的是 `r~U(8,25)`、`alt~U(8,30)` **独立采样**。这会采出大量废数据：
相机 -50° 几何要求目标水平距离在 `0.19×高度`(下边缘) 到 `2.66×高度`(上边缘) 之间才在画面里，
独立采样时 `r/alt` 跨 0.27~3.13，**`r=25/alt=8` 那类站位目标完全看不见**。

改成先采 `r~U(8,25)`，再在视野约束区间内采 `alt`：

```
alt_lo = max(8,  r/2.4)      alt_hi = min(30, r/0.3)
```

**离线用投影模型验证（5000 次采样）**：

| 方案 | 目标在画面内 | r 中位 | r<15m 占比 |
|---|---|---|---|
| 独立采样（07-30 写法） | — | — | — |
| 先 alt 后 `r=ratio×alt` | 100% | 23.1m | ~0%（**45% 被 clip 到 25m 上限**）|
| **先 r 后 alt（采用）** | **100%** | **16.6m** | **41%** |

第二种虽然也 100% 在画面内，但样本全堆在球面边缘，近场（指纹唯一有信号的区域）几乎采不到。
最终方案平均视线俯角 **49°**，正好压在相机光轴 50° 上 → 采样围绕"目标居中"对称展开。

### 连带改动（依赖被打断，已修）

### 存储格式决策

深度存 **uint16 米**而非 float32：07-30 实测量化步长本就是 1m，精度无损、体积减半
（300 条 × 200 帧：12GB → 6GB）。天空哨兵 65504 统一存 **0**，`depth_invalid` 写进 attrs。
深度与分割 resize **必须 `INTER_NEAREST`** —— 深度插值会在物体边缘造出不存在的中间距离，
调色板颜色插值出的中间色不对应任何 ID。

### 首跑实测（`--num 2`，两条全部成功）

体积 **6.7 MB / 条**（100 帧 × 三路，gzip 后 ~67KB/帧）→ 300 条约 **2 GB**，比估的 6GB 小。

**修掉的两个 bug**：

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 采完卡住不退出 | `finally` 里 `land_async()` 且**无超时**；站位高达 30m，降落磨很久 | 照项目约定「结束即断连不等降落」改成只 disarm（`record_approach.py` 早有此注释，写的时候没遵守）|
| 2 | `attrs["dt"]` 是标称值 | 实测 dt **0.1314s**（7.6Hz），标称 0.1 → **偏差 31%**，抖动 std 0.016s。动作是速度指令、位移=速度×真实时长，用标称值训世界模型会带系统偏差 | 新增 `dt_actual`（从 `time` 逐帧差的中位数算）|

**确认生效的三件事**（用刚采的真实数据交叉验证）：

1. **`setup_segmentation` 在采集流程里生效**：掩膜色与 07-30 单独探针**逐字一致** ——

   → **深度进控制时：减速用欧氏距离对（沿视线接近），但盲区预警要的是水平距离，
   必须由欧氏距离和视线角换算，不能直接用。**
3. 数据格式：depth `uint16` 值域 [4,62]/[27,518] 米，无效(0) 占 0.0%（-50° 下视画面里没天空）。

| 1 | 起点贴脸 | 无人机悬在机翼正上方 4.8m，53% 的起点落在飞机水平投影内 | `r∈[8,25]` 的下限小于飞机水平半对角 17.1m；更根本的是**把起点分布当成了状态分布** —— 闭环时无人机从球面进入，近距离状态是飞行途中经过的 | `r` 下限提到 15m，起点只铺在球面附近 |

| 4 | 方位有空洞 | 20 条的 8 个扇区分布 `[4,1,5,1,2,2,5,0]` | 方位角纯随机采样的涨落 | 改**分层采样**：360° 均分 num 格，每条落自己格内 → `[3,2,2,3,3,2,2,3]` |

不是参数问题，得靠向下测距/开环末段解决。当前 `SAFE_MARGIN=2` → 终点稳定落在离目标顶 3.3m，
所有目标、所有距离带方差为零。

### 更正 07-30 的一条判断：分割**不是**投影的冗余

07-30 曾判断「evaluator 用 OOB 投影就够，分割冗余、还费带宽」。实测推翻：

> **OOB 中心的投影点，只有 59/100 帧真正落在飞机掩膜上。**

因为飞机不是实心盒子，包围盒几何中心投影出来常落在机身轮廓的空隙外。用它采深度，
**41% 的帧会采到地面**，给出错误的目标距离。
→ evaluator 的真值质心/面积/可见性应以**分割掩膜**为准，投影只用于"目标在不在视野内"这类粗判据。
（同理，"投影点 vs 分割质心 13~20px 误差"不是误差，是盒心与可见表面质心的**固有几何差**。）

## §2026-08-01　世界模型流水线首次跑通 —— **阴性结果 + 根因定位 + 数据重采**

流水线（采集 → DINO 抽特征 → 训 predictor → 三判据评估）**第一次端到端跑通**。
结论分两半：模型能跑，但**动作条件失效**；根因不在模型也不在数据量，在**采集的动作采样结构**。

### 一、判据体系：单步不算数，多步才算

`verify_predictor.py` 只测单步（model vs identity），首轮报"降低 14.1%，通过"。
**单步结果不足以验证动作条件是否成立**，还需要多步预测评价。
真正的判据是 `wm/eval_wm.py` 的三条比值（`<1` 为过），在 h3~h30 上看：

| 比值 | 含义 |
| --- | --- |
| `model/identity` | 学到运动了吗 |
| `model/zero-act` | 真在听命令吗 |
| `model/swap` | 不同动作走不同路吗 |

### 二、第一版数据（模板采集 40 条）：动作输入等于没接

| 比值 (held-out, h3~h30) | 实测 |
|---|---|
| `model/identity` | 0.72 / 0.67 / 0.66 / 0.60 / 0.71 / 0.72 ✅ |
| `model/zero-act` | **1.00 / 1.00 / 0.99 / 0.97 / 0.92** ❌ |
| `model/swap` | **1.02 / 1.05 / 1.00 / 1.04 / 1.03** ❌ |

绝对值最直白，held-out h5：`model 0.77 / zero-act 0.77 / swap 0.73` ——
**给真动作、给全零动作、给别条 episode 的动作，预测误差完全一样，换错动作甚至略好。**
模型学到的是"画面会往前漂"的平均先验；它赢 identity 靠"知道场景在动"，不是"知道往哪动"。

**这对 MPPI 是致命的**：规划靠比较不同候选动作的 rollout 打分来选动作，
预测与动作无关 → 所有候选同分 → 规划退化成随机。

### 三、根因：动作在 episode 内几乎不变，且与视觉上下文绑死

模板采集数据的动作结构如下：

|  | airbase 第一版 |
| --- | --- |
| 每条 episode 的动作段数 | **2~3 段** |
| 动作在 episode 内变化 | 变 1~2 次，同属一个模板 |
| 组内/组间动作方差比 | **`[0.33 0.21 0.31 0.73]`** |

一条 episode 只跑一个模板 → 动作几乎等于 episode 的标签，而站位几何在画面里看得见 →
**模型学会"看图猜模板"就能预测运动，不需要读动作**。

另一个反效果：`NOISE_V=0.2` 是每步独立的白噪声，而飞控速度环要 ~11 步(1.5s) 才跟上指令
（实测位移/指令比值第 1 步 0.23 → 第 19 步 0.86），这种高频抖动被完全滤掉、产生不了可观测位移差异。
**它不是激励，是动作输入上的标签噪声**，等于反复教模型"动作扰动不影响结果"。

⚠️ 动作与真实位移的关系本身是**干净的**（方向余弦 0.94）。信号在数据里，是**采样结构**让模型学不到。

### 四、修法与验证（改 `collect_episode.py` 四处）

1. `TEMPLATES` → `SEG_POOL`（10 个动作基元）+ `build_random_traj()`：一条 episode 随机串 8 段，相邻不重复
2. `SEG_STEPS=13`：**下界由速度环决定**，短于 ~11 步指令还没执行到就换了，对应关系被暂态糊掉
3. `fit_to_station()` 不再分模板，按"全程直线冲向目标"的最坏情况缩放，系数**上限 1.0**（只缩不放；放大会把速度推过 4m/s，超出闭环动作范围）
4. `NOISE_V` 0.2→0.05、`NOISE_YAW` 0.1→0.03

**随机分段 60 条的结果**（同样 held-out）：

| 比值 | 模板 40 条 | 随机分段 60 条 |
| --- | --- | --- |
| `model/identity` | 0.72~0.60 | 0.68~0.60 |
| `model/zero-act` | 1.00~0.92 | **0.76~0.96** |
| `model/swap` | 1.02~1.03 | **0.91~0.98** |

**`zero-act` 从贴着 1.00 掉到 0.75~0.84 —— 改的只有动作采样结构，模型就开始读动作了。**
静态指标（方差比 0.33→0.86）在下游真的兑现。诊断成立。

**但 `swap` 只到 0.91~0.98**：模型能分辨"有动作 vs 没动作"，**分辨不出"这个动作 vs 另一个动作"**，
而 MPPI 挑候选靠的正是后者。且训练集 0.73 vs held-out 0.95 → **瓶颈已从"数据结构"转为"泛化不足"**。

### 九、300 条的结果：**"泛化不足"被否定**，真因是输入缺状态

`predictor_wm300`（300 条，best-ckpt）held-out 20 条：

| 比值 | tmpl40 | randseg60 | **wm300** |
| --- | --- | --- | --- |
| `model/identity` | 0.72~0.60 | 0.68~0.60 | 0.65~0.61 |
| `model/zero-act` | 1.00~0.92 | 0.76~0.96 | 0.83~0.76 |
| `model/swap` | 1.02~1.03 | 0.91~0.98 | 0.92~0.83 |

**关键不在这三行，在训练集与 held-out 的缺口**：

| `model/swap` | randseg60 | wm300 |
|---|---|---|
| 训练集 | 0.73 | 0.89 |
| held-out | 0.95 | 0.86 |
| 缺口 | 0.22 | **≈0（held-out 反而略好）** |

数据 ×5 后缺口消失，**但不是 held-out 追上来，是训练集掉下去**（0.73→0.89）——
模型**在见过的数据上也做不到动作特异**。这不是过拟合，是**欠信息**。
→ **加数据无效，60→300 已经证伪。§五 里"瓶颈转为泛化不足"的判断作废。**

更尖锐的信号在 `h1` 列：`model/zero-act 1.07`、`model/swap 1.05` ——
**单步内给全零动作、给错动作，都比给真动作准**。

#### 根因：单帧 latent 里没有速度，而单步位移由速度主导

对位移做线性回归（机体系平均速度 ~ 动作），三批数据横着比：

| 数据 | 段长 | 只用 `a_t` | `a_t..a_{t-3}` | 动作方差比 | 实际结果 |
|---|---|---|---|---|---|
| nearfield（模板） | 30~60 步 | **0.800** ✅ | 0.889 | **0.33** ❌ | zero-act 1.00 |
| randseg60 | 13 步 | 0.484 ❌ | 0.748 | 0.90 ✅ | zero-act 0.79 |
| wm300 | 13 步 | **0.468** ❌ | **0.737** | 0.90 ✅ | zero-act 0.79 |

**只用 `a_t` 时 R²=0.468，只用 `a_{t-1}` 反而 R²=0.576** —— 上一步的指令比这一步更能决定这一步怎么动。
飞控速度环 ~11 步才跟上指令，而段长 13 步，无人机**永远在追指令、从没追上过**。

**两次失败是同一原因的两面**，动作条件成立需要两个条件同时满足：

1. 动作在 episode 内要变 —— 否则模型"看图猜模板"就够了（nearfield 栽在这）
2. 每段要够长让速度环稳下来 —— 否则 `a_t` 不决定这一步（randseg/wm300 栽在这）

机场 episode 有 100 步，使用 8 段时每段约 13 步——
为拿到 ①，把 ② 弄丢了。

#### 修法 A（已实现）：喂动作历史

`forward(z, a_t)` → `forward(z, [a_t, a_{t-1}, a_{t-2}, a_{t-3}])`。

- 信息上限 R² 0.468 → **0.737**，直接补上缺的那块
- **不用重采**，动作序列本就存着，只需重训
- **对准真实工况**：闭环时 MPPI 每步换指令，无人机永远处在暂态，历史正是那时需要的
- **闭环合法**：历史指令是控制器自己发的，不是特权信息；MPPI 评估候选序列时第 k 步的历史
  就是它自己前面几步的候选值，训练与部署输入构造一致

实现：`stack_action_history(a, k)` 把 (T,4)→(T,4k)，开头补零（= 此前静止，与
`goto_station` 后有 rotate + 0.8s settle 的事实相符）；`--action-hist`（默认 1 = 旧行为）；
ckpt 记 `action_hist`/`action_dim`，`eval_wm` 与 `verify_predictor` 按它重建同样输入。
旧 ckpt 无该字段时回落 k=1，向后兼容（已验证旧权重仍能加载）。

**修法 B（备选，未做）**：200 步 × 30 步段重采，R² 上限 0.800（加历史 0.889）。
不先做的理由：要重采 1.6h，且训练数据会比部署工况"干净"，可能反而拉开分布差距。
A 不够时再叠 B，两者不冲突。

### 十、动作历史验证：**三条判据全部通过，世界模型立住** ✅

从头到尾只动 `--action-hist` 一个变量，其余（数据、latent、超参、轮数）完全不变。
held-out 20 条（5 目标 × 2 带 × 2），h3~h30：

| R² | 0.469 | 0.595 | 0.692 | **0.757** | 0.838 | **0.881** | 0.902 |

### 十一、特权评价器 `eval_run.py` 落地（07-29 待办第 1 条，欠了 5 天）

**动机**：`run.h5` 的 `reached=True` **混淆两种停止**（`--stop-alt` 高度停止 vs `mass≥阈值`），
两者都不等于"接触到目标部位"。07-29 就记着「没有它，后面所有成功率都没有论文意义」。

**特权边界**：目标 OOB 与真实位姿**只用于事后评价**，绝不进控制器 —— 这是 teacher-student
里合法的评价端用法，与"推理时用目标坐标"是两回事。

**真值来源不硬编码**：从任一条该目标的 `episode_*.h5` 读 attrs（`target_name/center/size/quat`）。
场景一改，重采一条即可，评价器不用动。

**输出两级**：

- **L0 健全性**（不依赖目标）：帧数/时长/步长、总路程、单步最大位移（跳变检测）、
  高度范围、NaN、穿地帧数。用于判"这条轨迹本身可不可信"
- **L1 任务判据**（用真值）：到部位锚点的**最小 3D 距离**及其发生的帧/时刻、终点距离、
  到 OOB 表面的最小间隙（负值 = 穿模）、最近点处速度（用位姿差分而非指令，
  因实测位移/指令≈0.77）、目标在视野内的帧占比、**多阈值成功判定**（`--d 1,2,3,5`，
  不写死单一 `d`）

**几何自检**（写进脚本注释）：把 OOB 八角转到世界系反算轴对齐盒，得 **34.08 × 34.20**，
与 §2026-07-30 实测逐位吻合 → 四元数约定与旋转矩阵正确。另验盒距离符号、锚点间距=轴长。
视野判定复用 `probe_depth_seg_flight.project()` 的几何（07-30 验证过机头红十字落在机头尖端），
但改用**归一化坐标**，绕开"224×224 是 16:9 各向异性压扁、宽高比变了而 vFOV 没变"那个坑。

#### 首次批量评价：42 条历史闭环记录

### 二、默认值与初始化步骤检查

**坑 1：起点在有效半径外，cost 恒定，MPPI 在优化噪声**
从出生点起飞、目标 65m 外、机头朝北 → `peak≈0.01`、`best` 卡在 1.0、
60 步只挪 8m 且方向朝北（目标在西南）。架构定案(07-28) 本就写着远段是坐标直线的**脚手架**，
但 `plan_closed_loop` 从没实现过这一步。→ 加 `--start-station`，复用采集的
`sample_station/goto_station`，起点分布 = 世界模型的训练分布。

**坑 2：动作边界对称 → 规划器选到分布外动作 → 模型利用**
`v_down` 训练分布是 **-0.48~+1.36**（负=爬升），我设成对称 ±1.4。
规划器立刻顶在 **-1.40** 一路爬（22m→34m），比训练里最猛的爬升还猛 3.7 倍。
模型在分布外的预测不可信，MPPI 正是在那儿找到"预测很美好"的方向。
→ 改按维度取实测 0.5%/99.5% 分位：
`v_forward [+0.25,+2.57] / v_right ±2.07 / v_down [-0.38,+1.28] / yaw ±0.65`，
训练动作 96.1% 落在界内。**改完东向不再跑偏、爬升从 11.6m 降到 2.5m。**

**坑 3：单个规划周期移动距离 < 噪声尺度**
量化（直线接近录制，18~32m 区间 40 帧）：

```
斜率      -0.0277 peak/米     每步(0.15m)信号 = 0.00415
残差 std   0.0478              ← 是信号的 11 倍
单步 SNR   0.087
→ 信号盖过噪声需单次移动 1.7 米，而当时一个周期只走 0.75m
```

与 07-29 否定结果的数字一致（当时测得单步 SNR 0.03~0.14）。
→ `--horizon 12 --init-vx 1.4 --replan-stride 3`（周期移动拉到 ~1.8m；
`eval_wm` 验过模型到 h30 仍 `model/identity≈0.5`，horizon 12 在验证范围内）。
**改完前进速度从 0.3~0.9 抬到 1.3~2.57，单步位移 0.1→0.3m，`dist` 出现清晰下降趋势。**

**坑 4（小）：`--goal-thresh` 默认 0.5 未按本次机场实验标定**，26.8m 处就判定"到达"收工。
实验时应设 0.0 让它跑满，用 evaluator 量真实距离，而不是用 cost 值当到达判据。

### 三、目标函数的形状（决定性测量）

`机头.jpg` 模板在直线接近录制上的响应 vs 斜距：

| 斜距 | 0~8m | 8~12 | 12~16 | **16~20** | 20~25 | 25~30 | 30~40 | 40~60 |
|---|---|---|---|---|---|---|---|---|
| `peak` | 0.269 | 0.414 | 0.451 | **0.527** | 0.519 | 0.312 | 0.208 | 0.184 |
| `mass` | **0.020** | 0.169 | 0.176 | **0.198** | 0.169 | 0.016 | 0.002 | 0.001 |

→ **目标函数是个碗，碗底在 20m。** MPPI 停在 20m 不是失败，是它在最大化指纹响应

### 四、数据覆盖的缺口（体检口径的疏漏）

## §2026-08-05　伺服"到达标准"审计：三条判据全部失效，根因还是那个碗

伺服 v2 实飞前的静态审计。**结论：现在没有一条能真正判定"接触到目标部位"的到达标准。**

### 一、代码里的三条判据（`servo_closed_loop.py:500-506`，按优先级）

| 判据 | 触发条件 | 默认 | 生效条件 |
|---|---|---|---|
| `contact` | 目标深度 ≤ `--stop-dist`，连续 3 张**独立**深度帧确认 | None（关） | 必须显式传 |
| `altitude` | `-dz ≤ --stop-alt`，纯高度、不看视觉 | None（关） | 必须显式传，俯视用 |
| `mass` | `mass_f ≥ --mass-stop` | 0.20 | **仅当前两个都没传** |

→ 不传任何参数直接跑，**唯一生效的到达标准是 `mass_f ≥ 0.20`**。

### 二、三个问题，都能用 08-04 §三那张表（本文件 `:1316-1319`）直接算出来

**问题 1：`mass ≥ 0.20` 够不到，且峰值在 16~20m。**
`mass` 实测最大 **0.198**（16~20m 档），阈值 0.20 —— 差一点点，基本不触发。
就算触发也在 16~20m，那不是接触，是碗底。且 `mass` 同样是碗形：0~8m 掉到 0.020，
**越靠近越判不出到达**。

**问题 2：同一个 `mass` 还驱动减速律，方向是反的。**
`compute_body_cmd:220` 的 `slow = max(0, 1 - mass/mass_stop)`，`vf = v_forward * slow`：

```
16~20m  mass=0.198 → slow = 0.01   前进/下降都只剩 1%，几乎刹停在碗底
 0~8m   mass=0.020 → slow = 0.90   反而几乎全速
```

**飞机会卡在 20m，一旦挤过去反而加速冲。** 这是"碗底在 20m"的同一根因，
但之前只在 cost 里点过，**没发现它也长在速度律里**。

**问题 3：`contact` 判据在最需要的最后 8 米自动失效。**
深度要过 `trust_depth = peak_f >= --dist-min-peak`（默认 **0.35**，`:453`），
而 0~8m 实测 `peak = 0.269 < 0.35` → `dist_t=None` → `contact_hit` 恒 False。
深度实际只在约 **8~25m** 被信任，**两端都自己关掉**：
远端 peak 0.18~0.31 太低（08-04 有意为之，防误判），近端 0.269 也太低（**副作用，未预料**）。

### 三、PX4 版更弱

`px4/servo_closed_loop_px4.py:268-271` **只有 altitude 和 mass 两条，没有 contact 判据**，
且 `--stop-alt` 一传就关掉 mass。08-01 已把 A 条件改用 API 版，但两份都还在，别拿错。

### 四、`--dist-min-peak` 的职责已经转移（但别删）

它是 08-04 加的（commit `09890fd`），当时是防误判接触的**唯一**手段。
v2 之后防线变成三道：目标分割掩膜（`:459-464`）+ `locked`（peak≥`--control-min-peak` 0.12，
`:490`）+ 3 帧独立确认。**掩膜堵死了当初那个失败模式**（噪声重心采到地面/别的物体）。

→ **仿真里**可降到 0.12（与 `locked` 对齐，消掉"关掉最后 8 米"的副作用）；
→ **`--no-seg-depth` 退化模式下它是唯一防线，所以参数保留、不删**。

另一个隐患：`--depth-half` 默认 **12**（25×25 窗口）是为**有掩膜**调大的；
无掩膜时窗口一半目标一半背景，中位数会乱跳 —— 退化模式应调回 3~5 或改取低分位。

### 五、根因归并

三个问题指向同一件事：**指纹的 `peak`/`mass` 在近距离塌掉（碗形）**。
它同时污染了 cost（08-04 已记）、**减速律**（本次新发现）、**深度门控**（本次新发现）。
治碗形不只是"让 MPPI 能对准部位"，**也是让伺服 A 条件能判定到达的前提**。

### 六、真机可移植性（**形态未定，以下是条件分析，不是结论**）

⚠️ 真机目标形态**尚未确定** —— 可能是地面上的颜色区域，也可能是某个 3D 目标物。
下面按两种可能各记一条，**任何一种都需要适配，代码不能直接搬**。

**共同的硬约束（与形态无关，这条是确定的）**：
UE 真值分割在真机上不存在。掩膜必须来自机载可得的东西 —— 颜色阈值 / 轻量检测分割模型 /
DINO 指纹热力图阈值化 / 或退化到 `--no-seg-depth`。所以
**`make_target_mask` 的"掩膜来源"必须保持可替换**，不能把 UE 真值写死进控制链路。
（相应地 `--dist-min-peak` 与 `--depth-half` 的取值随掩膜质量而变，见 §四。）

**若真机目标是地面颜色区域**（待定）：
`make_target_mask`（`:108-116`）本身就是颜色阈值匹配器，喂 RGB + 放大 tolerance
可能就够（实际部署大概率要换 HSV 抗光照）。且纯色区域尺度不变 → `peak` 不塌、
`mass` 单调 → `slow = 1 - mass/mass_stop` 方向正确、`mass_stop` 判据可用。
**若成立**，说明那套控制律不是写错了，而是被用在了不满足尺度不变性的 3D 部位上。
**未经真机验证，仅为推断。**

**若真机目标是 3D 目标物**（待定）：
碗形问题同构地存在 —— 模板在远距离拍、近距离外观塌掉，与 airbase 完全同类。
此时主线在治的碗形/补采 contact 带**直接服务于真机**，不是白做。

**与主线的关系（这条已确认）**：仿真是研究主体，实机是权重很小的验证环节。
**主线不为真机形态让路** —— 碗形与近场覆盖是仿真主线自身要解的问题，先按主线推进。

## §2026-08-06　L2 体检：动作可分辨性 SNR —— **世界模型对 MPPI 不可用（量化）**

### 动机：离线判据全过、闭环看不到效果，缺的是哪一级

已有判据只有两级，**都不回答 MPPI 真正需要的问题**：

| 级 | 内容 | 比的是什么 | 状态 |
|---|---|---|---|
| L0 | 多步 latent MSE | 预测准不准 | ✅ 有（但文献明说它**不预测规划成功**） |
| L1 | `swap` / `zero-act` | 真动作 vs **随机换一条别的** episode 的动作（**粗粒度**） | ✅ 有（swap 0.70） |
| **L2** | **动作可分辨性 SNR** | **MPPI 实际在比的几百条邻近候选之间** | ❌→本次补上 |

文献支撑：[ATM, arXiv 2606.09028](https://arxiv.org/pdf/2606.09028) 明确 latent MSE 不预测规划性能，
要看**动作可辨识性**；[RC-aux, arXiv 2605.07278](https://arxiv.org/html/2605.07278) 称此现象为
*predictive but not plannable*。

### 方法（新脚本 `loop/check_action_snr.py`，纯离线、不开仿真）

从 held-out 的 `z0` 出发，在 **08-04 重标的动作边界**内**均匀**采 100 条候选序列，rollout：

```
signal = spread : 100 条候选的终点 latent 之间的 std（换动作能让预测移动多远）
noise  = err    : 用**真动作**预测的终点 vs 真实 latent 的 RMSE（模型自己错多远）
SNR    = spread / err
```

同时报 **cost 域**（更决定性，MPPI 排的是 cost 不是 latent）：把终点 latent 过同一套模板
指纹读出（`peak`/`mass`，公式与 `plan_closed_loop.target_components` 一致）。
标准化一律用 **ckpt 的 z_mean/z_std**（与 `Planner.encode` 一致）。

### 结果（`predictor_wm300_h8e150`，72 起点 / 8 条 held-out / 100 候选）

| h | latent spread | latent err | **latent SNR** | peak spread | peak err | **cost SNR** |
|---|---|---|---|---|---|---|
| 1 | 0.0494 | 0.5171 | **0.096** | 0.0059 | 0.0420 | **0.142** |
| 2 | 0.2366 | 0.5865 | 0.403 | 0.0191 | 0.0555 | 0.344 |
| 6 | 0.2876 | 0.6967 | 0.413 | 0.0278 | 0.0671 | 0.414 |
| 12 | 0.3376 | 0.7703 | **0.438** | 0.0393 | 0.0760 | **0.517** |

产物：`outputs/evaluations/action_snr/action_snr.csv`

**三条读数：**

1. **h=1 塌到 0.096/0.142** —— 单步动作对下一帧的影响几乎测不出来。与"飞控速度环 ~11 步
   才跟上指令"（§2026-08-01 §十）吻合，是物理事实不是 bug。
2. **平台在 0.4~0.55** —— 模型预测误差是"换动作造成差异"的 **2~2.5 倍**。
   MPPI 按终点 cost 排序，而候选间 cost 差异只有模型误差的一半 → **排序主要由模型误差决定**。
3. **拉长 horizon 救不了**：spread 从 h2→h12 涨 1.43×，err 同步涨 1.31× ——
   分子分母一起长，SNR 只从 0.40 爬到 0.44。按此斜率要到 SNR=1 需 **h≈40**，
   远超模型验证范围（h30）与实用视野。

⚠️ 候选是**均匀**采样，比 MPPI 的高斯采样散得多 → **这已是乐观上界**，真实更差。

### 与 08-04 的对账：方向修对了，还差 2 倍

坑 3 在 **cost 侧**量到单步 SNR **0.087**；本次在**模型侧**量到 h=1 的 cost 域 SNR **0.142**，
同一量级、互相印证。08-04 的三个修法（`horizon 12 / init-vx 1.4 / replan-stride 3`）
正是冲这个去的，把 SNR 从 **0.087 抬到 ~0.52** —— **涨了 6 倍，方向完全正确，但仍差 2 倍**。

### 结论与它推翻的东西

**世界模型在当前配置下对 MPPI 不可用，且这不是 cost 的问题。**

→ **推翻"治碗形能同时救 A 和 B"这个判断**（本文件 §2026-08-05 §六写过）。
即便给 MPPI 一个完美单调的 cost，rollout 出的候选差异仍埋在模型自身误差里，**排不出正确顺序**。
治碗形**只对伺服（A 条件）成立**。

→ 与 A 条件实测对照（见下节 08-06 伺服复盘）：伺服离机头 **7.2m**，B 条件 **16.3m**。

### 局限（不要过度声称）

`err` 用的是**绝对**预测误差，而 MPPI 只需**相对排序**正确 —— 若误差在候选间是**共模**的，
排序时会抵消，则本指标偏悲观。纯离线数据无法测"任意候选动作的真实 cost"（那要真去执行），
这正是 ATM 那类诊断存在的理由。

→ **本结果是强证据、不是铁证**。要坐实需补一组"同起点、执行不同动作序列"的小规模仿真对照。
   但 h=1 的 0.096 与共模无关，那一条是硬的。

### 二、门控就是根因（用 8 次实飞的 `control[:,3]` 逐帧统计）

| | 门控 0.35 | 门控 0.12 |
|---|---:|---:|
| 深度可用帧占比（3416 帧） | **26%**（897） | **86%**（2937） |

两个死亡点上 `peak_f` 的实际取值：

- **`机头_0804_174253`**（撞机身，卡死区间 step 331→380）：
  0.266 / 0.186 / 0.185 / 0.187 / 0.185 —— **全部过 0.12**，
  而本文件 §2026-08-06 §三 记录这段 `dist_f` 全程 `-1.0`。
  **整整 70 步拿不到任何距离读数，而深度其实一直在那儿。**
- **`机头_0805_103801`**（降过头）：`peak_f` 到 step 350 仍有 0.126，
  step 360 之后才掉到 0.111 / 0.099 —— 门控 0.12 覆盖住出问题的那段下降窗口。

**0.12 不是随手调参**：按 `peak_f` 分档实测深度可用率，`0.00–0.12` 只有 **3/68 (4%)**，
`0.12–0.20` 是 80%，`0.20–0.35` 是 89%。**0.12 以下确实退化**，
所以原值"防误判接触"的保护没有丢，只是把门槛挪到了真正不可用的地方。
0.12 同时与 `--control-min-peak` 对齐 —— 同一个 `peak_f`，不该一个说"可以转向"、
另一个说"不能信距离"。

### 三、深度的量是准的，问题只在被关掉

`--stop-dist` 的代码语义是「指纹重心处深度 ≤ 此值」，测的是**指纹锁住的那块表面**多远。
实测：深度 vs 机头锚点 **ρ=0.992、MAE 1.9m**。

⚠️ **但它不是"到最近表面的距离"**：与 OBB `clearance` 比对有系统性正偏差且随距离增长
（clearance 0–5m 时 +5.15m；5–10m +6.43；10–20m +8.47；20–40m +9.23）。
**所以 `--stop-dist` 不是固定的物理间距**，阈值必须按"离锁定部位多远"实飞标定。

### 四、被否决的三条路（附实测，避免以后重走）

| 方案 | 否决依据 |
|---|---|
| **掩膜面积当距离代理** | **不成立**。整体秩相关只有 0.423（是被跨带趋势撑起的假象）；**带内接近 0**（10–15m 甚至 **+0.073**）；同一距离上面积散布 4–5 倍（0–10m 的 p10=4198 / p90=18093）。单条轨迹内部也弱：中位 ρ=**−0.434**，只有 24% 的 episode 达到 ρ≤−0.8。根因：机身 24m 长，视角/出画/遮挡都改面积 |
| **卡死检测**（指令速度≠0 而位移≈0） | 用户明确不要撞击 —— 那是在为撞击设计，不是为"停在阈值"设计 |
| **距离回归器当末段距离源** | 09-15 新训的 `weights/part_dist_22.pt`（`wm/train_part_dist.py`）在 **20–45m** 有效（ρ 0.68~0.93，val MAE 2.49m，优于 const 9.65 与 peak 9.40），逐 episode 单调性 **88% vs peak/mass 的 0%**；但 **0–15m 是纯外推** —— 训练集 0–10m 只有 4 帧、10–15m 只有 38 帧，且**没有一帧"看得见机头且<15m"**，真值 8.8m 处预测 17.9m。**救不了末段** |
